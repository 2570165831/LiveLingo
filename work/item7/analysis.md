# LAB-LOG 7：翻译失败可追查与自愈

## 改动前（e1e3b03）的结论

- 正式字幕由 `AppModel.drainTranslationQueue()` 串行处理。请求、公式还原、译文验收任一步抛错，都会进入同一个失败分支。运行库错误包括进程退出/管道断开、请求超时、协议或响应损坏、输出预算耗尽、运行库或模型不可用、可恢复的生成中断，以及未分类请求错误。
- 每段最多补试一次，**没有等待间隔**：验收失败改用内容修复指令，输出预算耗尽扩大预算，其余运行库/未知错误普通重试；模型缺失与取消不重试。补试结果仍须通过公式还原和译文验收。
- 两次都失败（或错误不可补试）后，段状态为 `failed`，从实时队列移除，不因后续字幕到达而自动再排队。停止录音后的自动收尾只排空现有队列，也不会重新加入这些失败段。因此会在当前处理轮次内永久缺少译文。
- `resumeSavedProcessing()` 会把所有缺少可用译文的段重新排队，包括失败段；打开未暂停、无恢复错误的课程会调用该入口。暂停课程、仅打开模式、旧课程来源缺失或恢复出错时不会自动开始。失败不等于数据丢失，但此前没有逐段固定原因及次数。
- `MLXRuntime` 已有进程自愈：退出或协议失败后清除旧 worker，终止本实例拥有的子进程；超时先取消请求，取消无回应或长期无活动则回收 worker；下一请求重新创建进程。旧进程退出最多等待控制超时（默认 5 秒）及强制退出后的 2 秒。立即补试可能撞上“正在退出”，导致该段的补试也失败；其他排队段仍能继续。
- **整条队列可停下的缺口**：依赖抛出 `CancellationError` 时，即使当前翻译任务并未被取消，worker 也直接结束。刚取出的段保留 `translating`、不再排队；剩余队列要等另一字幕、就绪检查或课后排空入口唤醒。真正的暂停/取消也缺少统一的已出队段归还逻辑，部分入口仅靠重新打开或继续处理补救。
- **超时补试的竞态**：运行库先向调用方报告超时，再等待取消确认。补试可能先于该确认及随后的进程回收，重新使用仍未释放旧请求的进程；只等待已经进入回收表的进程还不足以解决它。管道替身测试证实了这一顺序。

## 本次方案及边界

- 段内新增可选 `translationFailures`：固定原因枚举与各类出现次数，按最近出现顺序保存；重试成功也保留发生过的类别。新失败不写自由文字错误，不写模型输出或运行库 stderr。历史 `translationError` 只沿用既有兼容读写，不能据其猜测那次旧回放的原因。
- 保持已有 `translationState` 的四个旧值及会话 schema；新诊断与第 4 步的扩展字段一样由 0.2.0 忽略。无失败时不编码新键。未知未来原因归为 `unknown`。旧版再次保存会丢掉它不认识的新字段。
- 保留每轮最多一次补试。运行库失败补试前退避 1 秒，先有限等待已有取消/暂停确认，再等待本实例已在回收的旧 worker；确认等待上限为控制超时加 2 秒，进程退出继续使用既有有界回收。不额外停止健康 worker，不新增无限重启或轮询。验收/预算修复的请求与指令保持原样。
- 未真正取消的 `CancellationError` 作为该段失败记录，继续后续队列；真正取消时归还未完成段，记录取消类别，暂停期间不自动启动。恢复时可继续；失效会话/原文修订的旧任务不得写回。
- 普通日志及 CLI 专用失败事件仅新增原因枚举和整数计数；正常英文路径不新增事件或 JSON 字段。保存页类别展示为可选，本次不改 UI。
